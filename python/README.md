# VPT — Python port

A port of the VPT Java library to Python. The Java tree in `../src/` is the
**behavioural oracle**: it compiles, runs, and every ported file is verified
against golden values dumped from it.

## Install

From a release: each `python-v*` GitHub release has a wheel per platform
(Linux x86_64/aarch64, macOS arm64/x86_64, Windows x64; each covers
CPython 3.11+) and the sdist. Pick the wheel for your platform:

```sh
pip install vpt-<version>-cp311-abi3-<platform>.whl
```

From source, with [uv](https://docs.astral.sh/uv/) and a Rust toolchain
([rustup](https://rustup.rs/)); `uv sync` builds the extension with maturin
and installs the `dev` dependency group (pytest, pytest-cov, ruff):

```sh
cd python
uv sync
uv run pytest
```

Requires Python 3.11+ and NumPy.

### Native kernels

A few hot loops (path openings, area openings/closings, `ComputeSEs`) have
Rust implementations in `src/`, compiled into the `vpt._native` extension.
They return exactly what the Python code returns -- integer/boolean work
only, checked by `tests/test_native_parity.py` -- and are 30-45x faster
on those algorithms. The extension also carries the port's math functions
(`sin`, `atan2`, `pow`, ...): Java's, reproduced identically on every
platform, where `math`/numpy differ by OS (see "Transcendental functions"
under Known divergences). The Python code stays the reference and the
fallback: set `VPT_PURE_PYTHON=1` to run without the extension (math then
matches the goldens on Linux/glibc only), or `VPT_REQUIRE_NATIVE=1` to fail
if it can't be loaded. See `IMPROVEMENTS.md` sections 8 and 9.

Building from source compiles a few C files (CORE-MATH) besides the Rust:
gcc or clang on Linux/macOS, `clang-cl` (LLVM) on Windows, since MSVC's
`cl` can't compile them.

## Releasing

Versions are managed by [release-please](https://github.com/googleapis/release-please)
(`release-please-config.json` at the repo root). Don't bump the version by
hand: on every push to `main` it keeps a release PR open that bumps
`pyproject.toml`, `uv.lock`'s `vpt` entry, `.release-please-manifest.json`
and `CHANGELOG.md` together, from
[conventional commit](https://www.conventionalcommits.org/) messages since
the last `python-v*` tag. With squash merges, that's the **PR title**:

| Title prefix | Effect (while < 1.0) |
|---|---|
| `feat:` / `feat!:` | minor bump (0.1.0 -> 0.2.0) |
| `fix:` / `perf:` | patch bump (0.1.0 -> 0.1.1) |
| `docs:`, `test:`, `build:`, `ci:`, `chore:`, `refactor:` | no release on their own |

Merging the release PR tags `python-vX.Y.Z` and creates the GitHub release;
`.github/workflows/release-please.yml` then builds the platform wheels and
the sdist (`python-wheels.yml`, the same workflow CI runs), re-runs the
suite against each installed artifact, and attaches them with
`SHA256SUMS`. CI fails if the three version locations ever disagree.

## Quick start

Images are `ByteImage`/`DoubleImage`/`IntegerImage`/`BooleanImage`; every
algorithm is a class with a static `invoke(...)`, mirroring the Java API.
Pixel arrays are flat, indexed `x + xdim * y` (times `cdim` for colour).

```python
import numpy as np
from vpt.ByteImage import ByteImage
from vpt.algorithms.mm.gray import GGradient
from vpt.algorithms.segmentation import OtsuThreshold
from vpt.util.se.FlatSE import FlatSE

# A 32x32 grayscale image: a bright square on a dark background.
pixels = np.zeros((32, 32), dtype=np.int64)
pixels[8:24, 8:24] = 200
img = ByteImage(32, 32)
img.setByteArray(pixels.ravel())  # flat index = x + 32 * y

edges = GGradient.invoke(img, FlatSE.square(3))  # morphological gradient
mask = OtsuThreshold.invoke(edges)               # BooleanImage

print(mask.getXYBoolean(8, 8), mask.getXYBoolean(16, 16))  # True False
```

`tests/test_readme.py` runs this snippet, so it stays correct.

- `algorithms/mm/binary.{DistanceTransform,FeatureTransform}` -- chessboard/cityblock distance and feature transforms via repeated erosion/dilation. **Both carry HAZARDs on `BooleanImage` input** (the type `mm.binary` exists for), both traced to the already-documented `BooleanImage.getDouble` inversion: `DistanceTransform`'s loop condition `isEmpty(c)` reads through the inverted double view, so it reports "is every pixel True" instead of "is every pixel False" -- verified directly -- meaning **it hangs forever** on any mask with real background, the same failure shape as `BFillHole`. `FeatureTransform`'s loop condition (`isFull`, via `getXYCBoolean`) isn't inverted and so doesn't hang, but its body's `Subtraction.invoke(...)` is, so the boundary-pixel check is always `False` and it **silently stamps nothing** -- runs to completion, output entirely `0` -- verified with a 2-pixel repro and a 16x16 synthetic mask. - `algorithms/linear.*` -- complete (8/8). `Laplacian`/`MeanFilter`/`Prewitt` are thin `Convolution` wrappers, no new hazards (`Prewitt`'s `THETA` branch uses `Math.atan(py/px)`, not `atan2`, so a zero `px` -- any vertical edge -- is a real, common div-by-zero case routed through `jdiv`/`jatan`). `Gabor`/`RotationInvariantGabor` build a Gabor-filter kernel (one or more orientations summed) and convolve; **`RotationInvariantGabor` is a byte-for-byte duplicate of `Gabor`** in the Java (not a bug -- "rotation invariance" comes from the caller summing multiple orientations, which `Gabor` already supports), ported as its own duplicate file rather than a shared implementation, mirroring that class structure. Both accumulate their kernel through an explicit `Math` `(float)` narrowing cast Java performs at each step (`d += (float)gaborFunction(...)`; `float sum`) -- a genuine, deliberate single-precision-then-widen computation, not a decompiler artefact. New `_javacompat.jfloat` (the `(float)` double round-trip) and `jfloat_div` (a *true* single-precision division — `sum /= width * height` is `float /= int`, promoted to `float/float` by JLS 5.6.2, not `float /= (double)`, so double-precision-division-then-round-to-float can disagree with a single correctly-rounded float32 division by up to 1 ulp — the classic double-rounding pitfall) exist for this. `Canny` is the classic 5-stage pipeline (Gaussian blur, Sobel magnitude/direction, 4-bin direction quantisation, non-max suppression, `HysteresisThreshold`) with **two notable findings**: the Java's `Display2D.invoke(gradient, "", false)` mid-pipeline call is dropped (realises a real Swing/JAI `Frame2D` window, which leaves a non-daemon AWT thread running and hangs the JVM forever in a headless environment -- confirmed by hanging the oracle driver on first attempt) -- same category as the already-dropped `Display2D` call in `BReconstructionByErosion`; and a **bytecode-confirmed preserved bug**: of the four border-clearing loops at the end of the first pass, the one meant to clear the right edge instead repeats `setXYCDouble(0, ydim-1, c, 0.0)` every iteration (its loop variable is never read in the body), so the right image border is never actually zeroed. Golden-verified via `oracle/DumpLinear2.java` for everything except `Canny` itself, which can't be run by the oracle at all (the `Display2D` hang) and is smoke-tested only in Python.
- `algorithms/geometric.*` -- complete (8/8; `ConvexHull` was already done, golden-verified separately via `DumpRecovered.java`/`recovered.txt`). `Crop`/`Flip` are direct pixel-copy geometry ops (`Crop` normalises its two corner points via `min`/`max`, so either diagonal ordering gives the same rectangle); `ImageCentroid` is an intensity-weighted centroid returning a `Point`, using `jint` for the two `(int)` casts since a `DoubleImage` input isn't guaranteed to keep the sum non-negative; `ToPolar` resamples into 360 angle x half-diagonal radius bins via nearest-pixel lookup, clamped to the border. `Rotation` (inverse-mapped rotation into a resized bounding-box canvas, nearest-neighbour or bilinear) and `Resample` (independent X/Y resize ratios, nearest-neighbour/bilinear/bicubic -- the bicubic path is a two-pass Catmull-Rom-style interpolation, its result clamped to `[0, 1]` since it's the only method whose overshoot can leave that range) are both self-contained coordinate-math ports. `KeepLargestCC` is an 8-connectivity BFS flood fill over a `BooleanImage`, keeping only the largest component; its `LinkedList` FIFO queue is ported as `collections.deque` rather than a custom linked structure, since (unlike `mm/multi/connected/maxtree.MyList`) no node-level behaviour is exploited here. Golden-verified via `oracle/DumpGeometric.java` (extended) for the four new files.
- `algorithms/segmentation.*` -- complete (16/16 in-scope; 7 more on disk under `berkeley/` and `texture/TestOutexAngular.java` are out of scope, dataset-driven test harnesses / a prohibitively-slow gamut table -- see the closeout note below for the one exception, `berkeley.Seg2Image`, which *was* ported). `HysteresisThreshold` went first (needed by `linear.Canny`); the rest followed in one session: `Otsu` (threshold-selection half of Otsu's method in isolation -- note the Java's `new double['þ']`, JD-Core rendering an array-size push of 254 as a char literal since it fits `char`'s range, verified via `javap`; it's `new double[254]`), `SuperposeBorders`/`BorderToDominantNeighborLabel`/`NumberOfSingletons`/`MergeSingletons` (small watershed-line/label-map utilities), `LabelsToMeanValue`/`LabelsToMeanHue` (per-region mean colour/circular-mean-hue remap), `Watershed` (the classic Vincent-Soille immersion-simulation transform) and `MarkerBasedWatershed` (seeded watershed via a 256-bucket hierarchical FIFO queue), and `MeanShift` (colour-space mean-shift clustering). ## Design

**The API mirrors the Java one method-for-method.** `getXYCDouble`,
`FlatSE.square(3)`, `GDilation.invoke(img, se)`. That is deliberate: it lets
each Python file be diffed against its Java counterpart during review, which
is the only practical way to audit a port of this size. A PEP 8 facade can be
layered on later without reworking anything underneath.

**Storage is NumPy; structure is Java.** Each `Image` subclass wraps a typed
ndarray rather than a Python list, so the byte type gets Java's `(byte)`
wraparound from `int8` for free and algorithms have a vectorisation path. The
class and method structure stays 1:1 with the Java.

**Java overloads that dispatch on static type are split.** Python cannot
reproduce static dispatch, and the difference is not cosmetic: on a
`ByteImage`, `fill(1)` stores 1 while `fill(1.0)` stores 255. So `fill` is
split into `fillInt` / `fillDouble` / `fillBoolean`, with a runtime-dispatching
`fill()` wrapper for convenience. Same for `newInstance`.

## Preserved defects

Several behaviours here are wrong but faithful. They are reproduced because
the Java oracle exhibits them and callers depend on the observed results;
each is flagged in a comment at its site.

- `Image.getXYCMaximum` seeds its running maximum with `-1.797693134862316E+30`
  — exponent `E+30`, not `E+308`. Documented in the root README as preserved
  as found.
- `BooleanImage`'s non-boolean getters are inverted: `getByte` returns 255 for
  a **false** pixel. Downstream consequence, discovered while porting
  `ConvexHull`: because `setDouble` is *not* correspondingly inverted,
  `algorithms.arithmetic.Minimum` computes NOR instead of AND on a pair of
  `BooleanImage`s. That appears to make `BReconstructionByDilation`'s
  fixpoint loop non-terminating whenever it's driven with boolean marker/mask
  images — which is BFillHole's, and therefore `ConvexHull(...,
  filled=True)`'s, primary use case. See
  `python/vpt/algorithms/mm/binary/geo/BFillHole.py`. Not exercised by any
  oracle harness (`Recovered.java` only calls `ConvexHull` with
  `filled=false`), so unconfirmed against a JDK, but every piece involved is
  a faithful transcription, so this is expected to reproduce in the original
  library rather than be specific to the port.
- `Tools.VAddC` and `Tools.VSub` mutate their input in place and return a
  freshly allocated all-zero array.
- `Tools.drawLine` computes its slope with integer division before widening to
  float, so shallow lines come out horizontal.
- `Tools.getAngleABC` reads `cb.y` twice in its determinant.
- `IntegerImage.fillDouble` prints "Not yet implemented!!!" and does nothing.

Do not "fix" any of these without regenerating the goldens and explaining the
change — the test suite will fail, which is the point.

## Known divergence from the Java

Seven, so far:

**`GMaxTreeNonIncrAttrOpening`'s `DIRECT` filtering strategy: Java crashes,
Python doesn't.** Confirmed against the JDK 21 oracle (`oracle/DumpConnected.java`):
for a call with `filteringStrategy=DIRECT` against any tree with real internal
structure — the ordinary case, not a rare edge — Java's `processDirectlyNode`
throws `ConcurrentModificationException`. It mutates a node's `children`
`ArrayList` (via `addAll`) while an `Iterator` from that same list is still
walking it, without going through the iterator — only `Iterator.remove()`/
`add()` are safe mid-traversal. This port implements the clearly-intended
splice-out-and-continue semantics instead of reproducing a crash. See
`python/vpt/algorithms/mm/gray/connected/GMaxTreeNonIncrAttrOpening.py`.
`test_connected_golden.py` special-cases this one row: it asserts the golden
still shows the expected Java crash (a `THREW` sentinel written by
`oracle/DumpConnected.java`'s `dumpGraySafe`, not a bit-exact pixel row) and
that Python still produces real output, rather than comparing pixel-for-pixel.

**Transcendental functions (`Math.sin`, `Math.atan2`, `Math.pow`, ...):
resolved through `vpt._native`, except for rare intrinsic misroundings.**
These used to be the port's main source of divergence: `java.lang.Math`
isn't the platform C library, so `math.*`/numpy matched the oracle only up
to an ulp or two -- `linear.Sobel`'s `THETA` (`atan2(2.039…, -8.33e-17)`),
`ZernikeMoment(s)`, `OrientationMap`, `LoadFLO`, `point.Log`, `RGB2HSY`
and others carried 1-8 ulp tolerances -- and the libm differs by OS, so the
goldens that passed on Linux failed on macOS and Windows. The JDK 21
oracle computes `asin`/`acos`/`atan`/`atan2` with fdlibm (`StrictMath`)
and `sin`/`cos`/`tan`/`exp`/`log`/`log10`/`pow` with HotSpot's x86_64
intrinsics. `vpt._native` (`src/jmath.rs`) reproduces the fdlibm ones bit
for bit and computes the others correctly rounded (vendored CORE-MATH,
`csrc/core-math`), which is what the intrinsics return except in
hard-to-round cases: about 0.05-0.25% of random `sin`/`cos`/`tan`/`exp`/
`pow` inputs, where the exact value sits within ~1% of an ulp of a
rounding midpoint and the intrinsic picks the wrong side. With the
extension, every former tolerance above is gone (bit-exact on every
platform); the one remaining tolerance is `shape.ZernikeMoments` (<= 8
ulp), whose ~100,000 calls include 9 such misrounded `sin`/`cos`/`pow`
values -- confirmed by replaying each call through the JVM. That residue
is deterministic, identical on every OS and CPU. `tests/test_jmath_golden.py`
pins the functions themselves against `oracle/DumpJMath.java`. Without the
extension (`VPT_PURE_PYTHON=1`) the port falls back to `math`/libm and the
old tolerances apply (`tests/_platform.py:libm_ulp`), on Linux/glibc only.

**`point.Log`'s `Math.log10`: same 1-ulp fdlibm-vs-glibc divergence, different
function.** Confirmed against the JDK 21 oracle (`oracle/DumpPoint.java`):
`log10(11)` and `log10(0.75)` (from `DoubleImage` inputs `10.0` and `-0.25`,
each fed through `Log`'s `1.0 + pixel`) round their last bit differently
between Java and Python's `math.log10` (glibc), for the same reason as the
`Math.atan2` divergence above — `Math.log10` carries the identical JLS
1-2-ulp-of-correctly-rounded allowance, not exact bit-reproducibility.
`test_point_golden.py` uses the same `max_ulp=1`-on-affected-checks-only
pattern as `test_linhist_golden.py`.

**`conversion.RGB2HSY`'s `Math.acos`: same fdlibm-vs-glibc divergence, up to
2 ulp this time.** Confirmed against the JDK 21 oracle (`oracle/DumpConversion.java`):
of the 64 pixels in an 8x8 RGB gradient test image, exactly one (`(x,y) =
(6,7)`, `acos(-0.866025403784439)`) disagrees between Java and Python's
`math.acos` (glibc), by 2 ulp -- still within the JLS's 1-2-ulp-of-correctly-
rounded allowance for `java.lang.Math`, same reasoning as the `atan2`/`log10`
entries above. Propagates into `RGB2NUHSY733` (duplicates `RGB2HSY.convert`'s
formula) and `DistanceFromHSYColor` (calls `RGB2HSY.convert` on its reference
colour). `test_conversion_golden.py` uses the same `max_ulp`-on-affected-
checks-only pattern, set to 2 for these three.

**`statistical.ZernikeMoment`: same fdlibm-vs-glibc divergence, chained
through `atan2`/`cos`/`sin`/`pow`.** Confirmed against the JDK 21 oracle:
2 of 3 `(n, m)` test cases (`(5,3)` and, at the boundary, `(4,2)`/`(6,0)`
depending on the test image) disagree with Java by up to 2 ulp -- the
polynomial evaluation in `zer_pol`/`zer_pol_R` chains enough transcendental
calls that the same last-bit rounding slack shows up more often than in
the single-call cases above. `test_statistical_golden.py` uses the same
`max_ulp=2` pattern.

**`statistical.PCA`'s eigendecomposition may disagree with Jama's, same
reasoning as `NonFlatSE.decompose`'s SVD below.** Java uses
`Jama.EigenvalueDecomposition` (Householder tridiagonalisation + implicit-
shift QL); the port uses `numpy.linalg.eigh` (LAPACK, typically divide-and-
conquer or MRRR). Different algorithms need not round identically, and even
two algorithms that agreed exactly would still each have a free sign per
eigenvector and, for any repeated eigenvalue, a completely unconstrained
choice of basis within that eigenvalue's eigenspace. `PCA`'s own `sort`
step (re-implemented verbatim, including its `>=` tie-break) reorders by
eigenvalue afterward but resolves neither ambiguity. Not golden-tested;
smoke-tested only. The matrix-multiplication steps around the
eigendecomposition (covariance computation, the final projection) remain
genuinely bit-exact, via `statistical/_jama.py`'s from-scratch
reimplementation of `Jama.Matrix.times`'s exact accumulation order rather
than `numpy.matmul`/`@` — see that module's docstring. `ReversePCA` (pure
matrix algebra, no decomposition involved) has no such caveat and is fully
golden-verified, fed a hand-picked eigenvectors/mean pair rather than
`PCA`'s own (non-reproducible) output.

**`NonFlatSE.decompose` may return sign-flipped kernels.**

Java uses Jama's SVD, the port uses `numpy.linalg.svd`. An SVD is unique only
up to a joint sign flip of the leading singular vectors, so both are correct
and neither is canonical. Jama's own sign is not self-consistent — measured
against the oracle it is positive for `Gaussian(1)`, `Gaussian(3)`,
`Gaussian(4)` and negative for `Gaussian(2)`, `Gaussian(6)`, `box(1)` —
so matching it would mean reimplementing Jama's Golub-Reinsch iteration
including its sign quirks.

That is not worth doing, because the result is unobservable. The only caller,
`algorithms.linear.Convolution`, does:

```java
NonFlatSE[] subKernels = this.se.decompose();
subKernels = null;                              // line 47 of the original
if (subKernels == null) { /* non-separable path */ }
```

The separable branch is dead code, and has been since the original JAR. The
outer product `h ⊗ v` that a live caller would use is sign-invariant anyway.

The sign difference does propagate into `getCoords`, because a negative centre
value suppresses the leading `(0,0)` and leaves a trailing `null` slot. The
test asserts that each side produces the coords pattern *its own* sign
implies, which verifies the mechanism is ported faithfully without inventing
a convention that neither library guarantees.

### Why goldens rather than hand-written expectations

The failure modes this port has to guard against produce numbers that are
